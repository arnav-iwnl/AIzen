Q1 — What is this project about?

60-second version: AIzen is a self-hosted SIEM that ingests real server logs, decides — deterministically — whether each line is an attack or an operational fault, stitches the hits into an incident timeline with root-cause analysis, and labels every finding with the right MITRE ATT&CK technique. It runs entirely offline on one box: no hosted LLM, no Python at request time, no external API calls in the analysis path.

Concretely it does the following:

  • Upload + real-time ingest. Upload .log/.txt/.gz files (streamed with readline, so 100K+ lines do not exhaust memory) or push lines live over POST /api/realtime/ingest and watch SSE frames arrive. The demo lab replays payload pools through the exact same pipeline.
  • Classification. Every line gets a category, severity and confidence from the rule engine, plus a second opinion from the ONNX classifier: attack type, category, severity.
  • Incidents. Patterns are fingerprinted and deduplicated — Connection refused on port <NUM> collapses to one pattern with a count, not 4,000 rows.
  • Timeline. Events are time-windowed into buckets, stratified-sampled, and expanded with ±N context lines so you see what surrounded the error.
  • Root-cause analysis. localRootCauseService returns rootCause, evidence[], causalChain[], impact, recommendations[], techniques[], systemErrors[], confidence and analysisNotes.
  • ATT&CK mapping. One vocabulary, server/mitre/attackMap.js, serves both detectors, plus a separate SYS-* catalog for non-attack faults. Every recommendation carries a technique; every operational recommendation carries a SYS-* id.
  • PDF export of the incident report.

Service 1 The AIzen backend on :3000 — Express, REST + SSE, rule engine, ONNX classifier, RCA, ATT&CK, Telegram alerts, PDF export. Service 2 The React 19 + Vite dashboard, plus a third process for the lab: an intentionally vulnerable Express site on :5000 (/product SQLi, /search and /profile XSS, /download path traversal, /login brute force, /api/admin). It logs every request in Apache format, forwards each line to the realtime ingest endpoint, and declares which ATT&CK technique each route models — as ground truth, so a miss is visible on the live feed without influencing classification.

Q2 — Explain the architecture.

Short version: six layers — parse, store, decide (rules, then the model), map to ATT&CK, serve (REST + SSE), explain (timeline + RCA). The only mutable state is an in-memory ring; everything else is a pure function of a log line.

1. Ingest and parsers

ParserFactory auto-detects the format — Apache Error, Apache Access, Nginx, and OSSEC/Wazuh alert blocks — and extracts structured fields including the client IP. Uploads stream to disk and are processed line-by-line; the realtime path takes one line at a time.

The most consequential parser decision is the envelope / payload split. A SIEM alert block carries two different things: the alert description and wrapper text (message, what the UI and RCA render) and the log evidence itself (payload, what the model and the training labeler read). Before the split, the network learned the SIEM's wrapper vocabulary, and 1,792 of 2,123 false positives were a single benign Cisco switch syslog scored bruteforce. After it, false positives dropped to 157.

2. The in-memory LogStore

There is no database. server/store/logStore.js holds parsed entries, fingerprints, patterns and a preprocessor stream. Fingerprinting is the join key that makes everything downstream cheap: normalize.fingerprint() on the Python side and the same canonicalization in JS produce the same key, so upload and realtime paths dedupe identically.

3. The rule engine — server/rules/logRules.js

Pure regex, no model, no I/O. It returns { category, severity, confidence, matchedRule, securityTypes, status }. Two details that took real debugging: security matching runs against a URL-decoded copy as well as the original (access-log payloads are almost always percent-encoded, so %3Cscript%3E was invisible to the rules while the training-side labeler did decode — the two labelers disagreed); and CREDENTIAL_PROBE is shape-based, not a denylist. The old 22-item list matched bare words anywhere in the line, so info, test and admin/ triggered T1552.001, and the username info made Accepted publickey for info a credential probe. Train-time and serve-time labelers must agree or the model learns one thing while the rules assert another.

4. The ONNX deep classifier — second opinion only

v2/runtime/onnx_classifier.js loads model.onnx + meta.json through onnxruntime-node, in-process, on CPU. It serves both paths with the same model: classifyLine() for realtime, classifyBatch() for uploads. It always contributes its attack_type, but to call a line Security on its own — rules silent — it must clear V2_SOLO_MIN_CONFIDENCE (default 0.90, server/config/app.config.js:69). Otherwise the event is tagged v2Only and stays non-alerting, and it never lowers the rule engine's confidence. A verdict is argmax → that class's threshold → fire, not one-vs-rest, so thresholds are tuned under the runtime's actual decision rule.

5. The real-time hub

server/realtime/realtimeHub.js is the fan-out point. ingestLine() runs parser → rules → v2 → ATT&CK mapping, then publishes SSE attack / log / alert frames, keeps a 250-entry ring buffer, and maintains counters, a 10s rolling rate and a 60s windowed alert threshold at /api/realtime/snapshot. Errors map to levels through a severity→level table so a rule-detected threat the parser logged as info still surfaces as an error. Telegram notifications are plain text with a 5s cooldown, so attacker-controlled content cannot break message parsing.

6. Analysis services

contextSelector does the expensive reduction: fingerprint dedupe, time-window bucketing, stratified sampling, ±N context slicing, and causal-chain construction. detectorService blends the two detectors using a dataset-level holdout split, so validation measures generalization rather than memorization of one pooled corpus. timelineService and localRootCauseService consume that context.

7. server/mitre/attackMap.js — one vocabulary, two detectors

famKey() normalizes a rule securityType (SQL_INJECTION) and a model attack_type (sql-injection, bruteforce) into the same family space, with ALIASES bridging spellings: BRUTEFORCE→ADMIN_BRUTE_FORCE, XSS→XSS_PROBE, SCANNER→SCANNER_SIGNATURE. That is the whole reason one map can serve both.

The label space is open: config.is_valid_attack_type() accepts any T#### / T####.### id, and techniqueFor(){ id, name: id, tactic: "Unmapped" } rather than inventing a name. A new annotated corpus adds classes with no code change.

8. The vulnerable site

A separate Express service that logs every request in Apache format, forwards it to POST /api/realtime/ingest, and declares the technique each route models. Those declarations arrive as expectedTechniques — ground truth only, never an input to classification.

9. What the analysis path deliberately does not contain

No LLM. AIClient exists and can be configured; with no API key the classifier and the narrative services fall back to their local implementations, which is the default and what CI exercises. An earlier version of the architecture doc wrongly claimed LLM-assisted analysis — that claim was removed because it was not true of the code.

Q3 — Why was this architecture chosen over others?

The one-line judgement: every structural choice here is a bet that a SIEM must be deterministic, auditable and self-contained. The model is deliberately fenced in as a bounded second opinion, because the cost of a false "this is an attack" in a SOC is much higher than the cost of a missed line the rules will catch anyway.

(a) Rules are the PRIMARY detector, not a legacy fallback

The rules key on payload syntax — SELECT ... FROM, ../, <script>, Invalid user — not on domain vocabulary. That is why they read a SIEM dump in a format nobody anticipated. A model keyed on learned vocabulary degrades exactly where you need it most: an unfamiliar dump. So the model may add an attack type to a line the rules already flagged, but to classify a line as Security by itself it must clear V2_SOLO_MIN_CONFIDENCE (0.90); otherwise the event is retained as a non-alerting v2Only signal. Technique attribution follows the same hierarchy: when the rules matched, their families decide the technique. Otherwise a model that reads a SQL-injection payload as bruteforce bolts a wrong T1110 onto a correct T1190.

(b) In-memory store, stateless services — because there is no database

Deliberate, not a shortcut. A demo-scale SIEM that ingests a file and reports on it has no persistence requirement, and dropping a database removes a whole class of deployment failure on a free-tier box: no connection pool to exhaust, no migration to run, no state to lose. It forces every service to be a pure function of a log line, which is also what makes the seven verification gates reproducible — feed the same file, get the same report. The cost is real: history is bounded by the ring buffer, and multi-node deployment would need a real store. That is a Phase-2 decision, not a Phase-1 one.

(c) ONNX + onnxruntime-node in-process, versus a Python sidecar or a hosted LLM

Three alternatives, three rejections. A Python sidecar means a second runtime, a second dependency set, a port, an IPC serialization cost per line, and a process that can die mid-upload. A hosted LLM means the analysis path stops being deterministic, stops working offline, adds per-token cost and latency on a per-line workload, cannot be batch-evaluated against a stored baseline, and leaks log content off-box. An in-process INT8 ONNX graph on CPU has none of that: no network, no cold start beyond one session load, ~640 KB of artifact, and it runs on a free-tier Render box. The Python training code never ships — it runs offline in v2/ and emits an artifact.

(d) Deterministic local RCA over LLM narrative

localRootCauseService is a rule book: PLAYBOOKS keyed by family, FAMILY_SCAN regexes to extract concrete targets (routes, files, IPs) from raw logs, then _techniques() and _recommendations() built from those. Every attack recommendation carries a technique; every operational one carries a SYS-* error. That gives an analyst an action ("parameterize the dynamic SQL on /product; restrict the DB user to least privilege") rather than a paragraph, and it gives a test something to assert on. An LLM can only be judged by vibes; this can be asserted by check:mitre.

(e) One normalized family space, so one ATT&CK map serves both detectors

The alternative — a rule-to-technique map and a separate model-to-technique map — guarantees divergence: two lookups to keep in sync, two chances to label the same event differently depending on which detector fired. Normalizing both into famKey() space with three aliases means there is exactly one place where "what technique is a SQL injection" is written down. It also makes the label space open: an annotated corpus that ships T1021.002 rows adds a class with zero code change, because the attack head is sized from labels.json and the runtime reads whatever meta.json contains.

(f) A separate SYS-* namespace instead of forcing everything into ATT&CK

An nginx upstream timeout is an operational fault. Calling it T1190 is not a simplification, it is a false statement that an analyst will act on — and it poisons every downstream metric built on technique counts. So RCA returns two lists that are never merged: techniques[] and systemErrors[]. The nginx system errors that were escalated to Security are exactly the bug this separation exists to prevent.

The trade-off I accepted

A closed-class model cannot be dump-agnostic, so the rules carry the load. The attack head is a softmax over a finite label set read from labels.json. A novel attack that matches no class is forced into other by definition. No amount of threshold tuning fixes that; it is a property of the output layer. I accepted it deliberately, because the alternative — an open-vocabulary embedding model — would need a hosted API, break offline operation, and make ATT&CK mapping unresolvable at inference time. The mitigation is structural: the rules are format-agnostic and stay primary, the model only escalates above 0.90 solo confidence, and the open T#### label space means new known techniques are a data change rather than a code change. Unknown-unknowns are the rules' job; the model covers known-unknowns better than regex does.

Bugs found and fixed — the evidence for the above

These are the concrete results of holding the architecture to its own claims:

  • A sentinel verdict masquerading as a real one. A attack_type: "rule" was written into the v2 verdict registry for rule-only hits, so consumers read it as a deep-model verdict: the timeline printed "Deep classifier detected rule attack (0.0% confidence)" and nginx system errors were escalated to Security. Fixed at the source; check:join now guards the invariant that the registry holds only real model verdicts.
  • The model was classifying the SIEM envelope, not the log. 1,792 of 2,123 false positives were one benign Cisco switch syslog scored bruteforce. Fixed by splitting message from payload and training on the payload.
  • The exporter never wrote attack_thresholds. The file was hand-edited, so any re-export silently deleted the tuned per-class values — and because onnx_classifier.js:121 falls back to attack_threshold (the strictest bar in the file) for any missing class, every newly trained class would have been effectively undetectable. The exporter now emits an entry for every class, and the fallback warns instead of absorbing the inconsistency.
  • INT8 quantization was silently skipped on every export. Two independent causes: the torch dynamo exporter emitted shape metadata the quantizer rejected (Inferred shape and existing shape differ in dimension 0: (256) vs (7)), fixed with dynamo=False; and default shape inference compared the sequence dim against the class dim, fixed with MatMulConstBOnly: True. The artifact was ~1.2 MB FP32 where ~640 KB was intended.
  • formatTimelineTimestamp() returned "" — so every event in a timestamp-less log shipped a blank timestamp. This was failing the project's own smoke test.
  • Rule gaps found while building the real-time path: the SQLi rule required OR followed by a digit and so missed the canonical OR '1'='1; security matching did not URL-decode, so %3Cscript%3E was invisible; CREDENTIAL_PROBE matched bare words like info/test/admin/.

Q4 — What would you like to improve in this project?

Short version: one packaging bug that breaks deployment, one architectural coupling that makes part of the label space unreachable, and a corpus-volume problem that no amount of code will fix. Listed in that order, because the first blocks everything else.

1. v2 is a stale gitlink — the model cannot reach Render from a fresh clone

git ls-files -s shows 160000 bad021903a7ecacc3dca20eed1c3a14ee7875b46 0 v2: v2 is recorded as a submodule, but there is no v2/.git and no .gitmodules. The model is therefore untracked, and a fresh clone cannot build the artifact the service needs at boot. Fix: convert the entry to a normal tracked directory (git rm --cached v2, then commit v2/ with an .gitignore that excludes datasets/ and data/ and keeps runtime/model.onnx + runtime/meta.json — those are the only two files the Node runtime reads), or restore a real submodule with a .gitmodules and a pinned commit. I prefer the flat directory: it is one less moving part, and the model is small enough to live in the repo.

2. The technique head is coupled to is_attack

This is the next architectural step, not a bug. In v2/train/models.py, is_attack is derived at runtime as attack_type != "none" — a single head holds both the binary decision and the subtype. The consequence: the ~10 techniques annotated on non-attack rows — T1595 Active Scanning, T1082 System Information Discovery, T1583 Acquire Infrastructure, T1053, T1562, T1071, T1005, T1059 — are unreachable by construction. Discovery and resource-development techniques are, by ATT&CK's own definition, frequently benign in isolation, and this head can never emit them. Proposed change: a fourth head, technique_head, trained against its own label set independent of the attack decision, with a gate on whether the technique is emitted at all. The serving side is ready — attackMap.BY_ID already carries those ids and the runtime reads the label space from meta.json — so this is a training-graph change plus one more output tensor in the ONNX signature.

3. Five technique classes are volume-starved

T1486 (Data Encrypted for Impact), T1041 (Exfiltration Over C2), T1021 (Remote Services), T1110 (Brute Force) and T1068 (Exploitation for Priv Esc) have only 30–60 labelled rows each. prep/dataset.py auto-demotes anything under the V2_MIN_CLASS_ROWS floor (default 200) into other, so these occupy no output slot rather than becoming confident noise. This needs corpus volume, not code. Next step: per-technique generation in each source corpus's own line shape — exactly the move that took brute force from ~186 to 799 rows and Wazuh recall from 0% to 100% — plus active collection from the OSSEC/Wazuh rule packs that already carry technique annotations.

4. The brute-force fix needs re-validation

The class was historically thin. The fix was to generate auth rows in the corpus's own shapes (_gen_auth_rows in v2/ingest/normalize.py, driven by V2_AUTH_ROWS, with the label re-derived by the same heuristic that labels the real corpus so synthetic and real rows cannot disagree), taking it to 799 rows. It produced 100% Wazuh recall, but that is measured on the generated distribution. It needs a held-out Wazuh dump that was not in the corpus at all before I claim it generalizes.

5. other is still a grab-bag at ~0% recall

Its share fell from 45% to ~10.6% of the corpus, but the class itself is close to unlearnable — it is a union of unrelated things, so nothing generalizes into it and the model learns nothing from it. Better: keep demotion as the safety valve, but split the residual into a small number of real classes as evidence accumulates, and treat any class whose recall stays near zero as a prompt to delete it rather than ship it.

6. Small cleanups

  • v2/runtime/onnx_export.py is a dead transformers scaffold. The real exporter is v2/export/export_onnx.py. Delete it — a second "how to export the model" file that does not work is worse than no file.
  • v2/runtime/meta.json still carries the category label Unknown while the app now shows Clean. The meta is the model's label space, so either the model is retrained with the new label or the UI maps back; right now the two disagree on the same word.
  • client/src/views/DemoView.jsx is an orphan — superseded by DemoLabView.jsx and no longer routed.

Proposed order of work

  1. Fix the gitlink (unblocks deploy; minutes).
  2. Retrain once with the current corpus and re-run the full gate set, so Q4’s claims sit on a fresh check:model baseline rather than an older run.
  3. Decouple the technique head from is_attack — the one change that makes 10 annotated classes reachable.
  4. Grow the five starved technique classes in their own line shapes; re-measure per-class holdout recall.
  5. Add a hash-n-gram side channel (see Q5) and A/B it against the pure-byte model on the same holdout.
  6. Land the cleanups.

Q5 — How is model training, datasets, understanding why LSTM is used?

Short version: heterogeneous public and local log corpora are normalized into one ballot, tensorized into a 256-char byte window, trained offline in PyTorch as a 617k-parameter bidirectional char-LSTM with three heads, exported to a 640 KB INT8 ONNX graph with tuned per-class thresholds, and loaded in-process by Node. Character-level input is the choice that removes the vocabulary problem entirely.

Corpora

Attack: HuggingFace web-attack detection sets, Kaggle malicious/phish URL datasets, plus synthetic obfuscation (_obfuscate() — base64, URL-encoding, comment insertion) and hand-shaped syslog/nginx/SIEM attack templates. Benign: Loghub (LogPAI) Apache, OpenSSH and NASA HTTP for real operational baselines, plus local OSSEC/Wazuh ingest and a set of plain request lines. The benign side is the part that was originally missing, and adding it is what took the benign false-positive rate from 10.28% to 2.17%.

Labeling for unlabeled data is done by a deliberately obfuscation-tolerant heuristic in normalize.py that URL-decodes before matching, so it labels the same text the serving rules see. prep/dataset.py then trains on payload when present and message otherwise, so the model never learns a SIEM wrapper.

Label space

Seven attack classes plus none: sql-injection, xss, path-traversal, bruteforce, scanner, credential_probe, other, with none at index 0. Two things make it forward-compatible: attack_index in meta.json is data-driven — built from the labels the corpus actually contains, not a hardcoded list — and config.is_valid_attack_type() accepts any T####/T####.###. So ATT&CK technique ids are first-class attack_type values, and a new annotated source adds classes with no code change. The old hardcoded membership test silently folded all of them into other, which is a large part of how other reached 45% of the corpus.

Masked pooling was itself a fix. The original x.mean(dim=1) averaged PAD positions in, so a typical 176-char line contributed ~31% of a 256-wide window — the pooled vector was length-dependent and shifted off-manifold on log formats of a different length. Deriving the mask from the ids (rather than adding a second graph input) keeps the ONNX signature at one input, so onnx_classifier.js needed no change.

Validation, and why the split is not random

The gate that changed how I measure. A prior retrain scored 0.983 on the old in-domain validation split while its cross-domain false-positive rate got worse (10.8% → 14.8%) and recall fell (90.4% → 73.0%). A random-row split literally cannot see that failure, so prep/dataset.py now holds out a fraction of every dataset (HOLDOUT_FRACTION, 0.15) plus one small fully-unseen domain (HOLDOUT_EXCLUDE, wazuh-tpfp), and npm run check:model is a cross-domain gate against a stored baseline. Holding out 100% of SIEM data while expecting SIEM detection is incoherent and measurably so: that configuration reached train F1 0.989 and holdout F1 0.417 with 1,998 false positives, because its only exposure to syslog/OSSEC line shapes was ~25 synthetic seeds.

Groups are split by src_ip/host (falling back to fingerprint), so one attacker's events never straddle the boundary. Thresholds are calibrated in export_onnx.py on that same holdout, under the runtime's actual argmax → threshold → fire decision rule: per-class one-vs-rest tuning measured F1 of 0.02–0.36 for every class because it optimizes the wrong objective, so it sweeps a global binary-F1 threshold, then does two coordinate-ascent passes. The resulting per-class values are written to meta.json.

Why an LSTM, and why at the character level

Three reasons, in order of how much they mattered.

1. No vocabulary, therefore no OOV problem. Input is raw bytes, base 256, with a 258-slot embedding (bytes + PAD + UNK). There is no vocabulary file, no tokenizer drift between Python and Node, and nothing to maintain as new logs appear. Unseen source IPs, novel paths, new encodings, mixed languages and unusual punctuation all tokenize because they are just bytes. check:tokenizer exists to keep the Python trainer and the JS runtime bit-identical; with byte-level input that check is nearly free, which is part of the point.

2. Attack signatures are local substrings, and an LSTM reads them in order. OR '1'='1, ../, Invalid user — the evidence is a short ordered character run embedded in a longer line. A bidirectional LSTM builds context from both directions over that run while mean-pooling collapses the whole 256-char window into one vector, so a payload anywhere in the line is visible regardless of position. That is also why the masked-mean fix mattered: without it, position and length changed the pooled representation.

3. It fits the deployment budget. ~617k parameters, 96.5% of them in the encoder, quantizing to a 640 KB INT8 graph that runs on CPU in-process. A transformer encoder over characters is a plausible alternative — the code even keeps the branch — but at this parameter count the LSTM is the better fit: it trains on a small corpus without over-parameterizing, exports cleanly to ONNX, and quantizes well. I would revisit the transformer only with a substantially larger corpus.

The trade-off I found, honestly

Byte-level input with a 64-dim embedding has a real cost: every keyword must be learned character-by-character from shared, overloaded byte embeddings. The embedding table has 258 rows × 64 dims, and the same 256 rows carry ' in a SQLi payload, the ' in a shell-quoted syslog string, and the ' in English prose. A 617k-parameter model has to learn the phrase "this byte sequence in this context means SQL injection" from scratch, and it has to relearn it for every log format, because the context that gives the byte meaning changes when the line format changes. I believe that is a plausible cause of the weak cross-format generalization measured in Q3's gate — in-domain numbers look excellent while the held-out SIEM FP rate does not move.

The proposed fix is a hash-n-gram side channel: a second input of hashed character n-grams (say 3–5) computed with a fixed, code-free hash, so multi-character patterns get their own embedding rows instead of being reconstructed from shared bytes. It is a few lines in preprocessing plus one more input tensor, it survives ONNX export, and it needs no vocabulary file — which was the whole reason for choosing byte-level input in the first place. The decision rule is to A/B it on the same holdout with the same gate: if it does not beat the pure-byte model on cross-domain FP rate and per-class recall, it does not ship.
